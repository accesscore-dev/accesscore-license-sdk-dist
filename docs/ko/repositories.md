# 저장소 두 곳

소스와 릴리스를 나눈다.

| 저장소 | 공개 여부 | 담는 것 |
| --- | --- | --- |
| `accesscore-dev/accesscore-license-sdk` | 비공개 | Rust 코어, 모든 바인딩 소스, 적합성 벡터, 가이드 |
| `accesscore-dev/accesscore-license-sdk-dist` | 공개 | 미리 빌드한 코어, C 헤더, Go 바인딩, 가이드, 벡터 |

## 공개 저장소가 왜 필요한가

Go 때문이다. `go get`은 모듈을 소스로 받아오므로 Go로 쓰는 쪽에는 읽을 수 있는 트리가 있어야 한다. Java와 Python은 패키지 레지스트리로 해결하니 두 저장소 어느 쪽도 보지 않고, 조직 안의 Rust 사용처는 비공개 저장소에서 받는다.

Go 때문에 공개 트리가 어차피 있어야 하므로, 쓰는 쪽을 향한 것은 모두 그리로 간다: 미리 빌드한 라이브러리, SDK가 지원하지 않는 언어를 위한 헤더, 가이드, 그리고 적합성 벡터 — 자기 연동을 검증하는 쪽이 이 벡터를 돌리며, 토큰의 의미에 대한 약속을 읽을 수 없다면 그것을 근거로 삼을 수도 없다.

## 절대 건너가지 않는 것

Rust 코어 소스와 발급 경로는 비공개에 남는다. 공개 저장소에 있는 것으로는 라이선스를 만들 수 없다 — 서명에는 개인키가 필요하고, 개인키는 어느 저장소에도 들어간 적이 없다. 적합성 키는 벡터 외에는 아무것도 서명하지 않으므로 함께 나간다.

## 릴리스가 흐르는 길

```
비공개 저장소에 v1.2.3 태그
  ├── 여섯 플랫폼 코어 빌드                  (플랫폼당 한 잡, 병렬)
  ├── 같은 산출물로 각 바인딩 패키징          (두 바인딩이 서로 다른 코어를 싣지 않게)
  ├── dev.accesscore:license-sdk 발행         → GitHub Packages
  ├── accesscore-license 발행                 → wheel, 릴리스에 첨부
  ├── 쓰는 쪽 트리 조립                        scripts/assemble-dist.sh
  ├── 공개 저장소에 푸시                       새 커밋 하나, v1.2.3 태그
  └── 릴리스 생성, 플랫폼 산출물 첨부
```

공개 저장소는 릴리스를 담지 그것을 만든 개발 과정을 담지 않는다 — 릴리스마다 커밋 하나이지 이력을 옮겨 심지 않는다. Go 모듈 경로는 조립 중에 바뀌므로, 쓰는 쪽의 `go.mod`는 공개 저장소를 가리키고 비공개 저장소는 가리키지 않는다.

## CI에 필요한 것

| 시크릿 | 출처 | 용도 |
| --- | --- | --- |
| `GITHUB_TOKEN` | 자동 제공 | GitHub Packages 발행, 릴리스 생성 |
| `DIST_REPO_TOKEN` | 직접 설정 | 공개 저장소 쓰기 권한, 그 외에는 아무 권한도 없음 |

`DIST_REPO_TOKEN`을 한 저장소로 한정하는 것은 의도한 것이다. 아무 데나 쓸 수 있는 릴리스 단계는 다른 무언가로 바꿔 쓸 수 있는 단계다.

## 버전 번호

코어와 네 바인딩이 태그에서 온 하나의 버전을 공유한다. 바인딩이 따로 릴리스될 수 있으면 쓰는 쪽이 Java 래퍼와 다른 스키마를 읽는 코어를 짝지을 수 있고, 스키마 번호야말로 어긋나서는 안 되는 값이다.
