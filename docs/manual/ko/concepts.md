# 공통 개념

라이선스의 형식과 판정은 하나의 코어가 소유한다. 네 언어 바인딩은 호스트가 아는 것을 코어에 넘기고 무엇을 해도 되는지 돌려받는다. 라이선스에 관한 판단은 두 번 내려지지 않는다.

## 코어가 소유하는 것, 호스트가 소유하는 것

| 코어 | 호스트 |
| --- | --- |
| 페이로드 형식과 스키마 번호 | 기록 저장·로드 (JPA · 파일 · 레지스트리) |
| 서명 생성과 검증 | 현재 시각 |
| 머신 식별자 수집과 대조 | HTTP 전송·재시도·타임아웃 |
| 만료·유예 기간, 채널별 완화 | 하트비트 주기 실행 |
| 하트비트 기한 계산 | 게이트 부착 위치 |
| 시계 되돌리기 판정 | 바이너리 무결성 계산 |
| 제품 코드·릴리스 상한 대조 | 감사 기록 |
| 거부 상태와 메시지 키·인자 | 메시지 번역 |
| 활성화·하트비트 요청 본문 생성과 응답 해석 | |

바이너리 무결성만 호스트 몫인 것은 계산 대상이 언어마다 다르기 때문이다. JAR 해시와 실행 파일 해시와 wheel 해시는 같은 방법으로 구할 수 없다. 호스트가 검사 결과를 판정 입력에 실어 넘기고, 코어는 그 결과를 다른 검사와 같은 순서에 놓는다.

## 토큰

```
base64url(payload).base64url(signature)
```

서명은 전송되는 페이로드 바이트 원본을 덮고, 그 바이트가 그대로 토큰에 실린다. 검증기는 아무것도 다시 직렬화하지 않으므로 정규화 규칙이 필요 없고, 키 순서가 다른 JSON 작성기를 쓰는 언어가 서명을 깨뜨리지 못한다.

## 판정

한 순서로 열다섯 단계다.

```
 1. 바이너리 무결성 (호스트가 넘긴 결과)   실패     → INTEGRITY_FAILED
 2. 저장된 토큰                            없음     → NOT_ACTIVATED
 3. 폐기 기록                              남아 있음 → REVOKED
 4. 토큰 파싱                              실패     → NOT_LOADED
 5. 스키마 번호                            읽을 수 없음 → SCHEMA_UNSUPPORTED
 6. alg 허용 목록 · kid 조회 · 짝 확인      어긋남   → INVALID_SIGNATURE
 7. 서명                                   실패     → INVALID_SIGNATURE
 8. 제품 코드                               다름     → PRODUCT_MISMATCH
 9. 채널·와일드카드 정합성                  어긋남   → INVALID_SIGNATURE
10. 머신 핑거프린트                        불일치   → MACHINE_MISMATCH
                                           수집 실패 → FINGERPRINT_UNAVAILABLE
11. 만료·유예                                       → VALID / GRACE_PERIOD / EXPIRED
12. 릴리스 상한                            초과     → RELEASE_NOT_ENTITLED
13. 시계 워터마크                          역행     → CLOCK_TAMPERED
14. 하트비트 기한                          초과     → HEARTBEAT_OVERDUE
15. 워터마크 갱신                                   → max(현재 시각, 기존 기준점)
```

스키마 번호를 서명보다 먼저 보는 것은 읽지 못하는 형식에 서명 검사를 시도할 이유가 없어서다. 제품 코드는 서명 직후, 머신 바인딩 앞에 둔다 — 다른 제품의 토큰이라면 머신이 맞는지는 물어볼 필요가 없다. 13·14단계는 12단계까지 사용 가능한 상태가 나온 경우에만 본다.

## 상태

| 상태 | 의미 | 사용 가능 |
| --- | --- | --- |
| `VALID` | 모든 검사 통과 | ● |
| `GRACE_PERIOD` | 만료했으나 유예 기간 안 | ● |
| `RELEASE_NOT_ENTITLED` | 계약 상한을 넘는 릴리스 | ● |
| `EXPIRED` | 유예 기간까지 지남 | ○ |
| `INVALID_SIGNATURE` | 서명 불일치, 허용하지 않는 알고리즘, 프로덕션 채널의 와일드카드 | ○ |
| `MACHINE_MISMATCH` | 각인된 핑거프린트와 이 머신이 다름 | ○ |
| `FINGERPRINT_UNAVAILABLE` | 머신 식별자를 하나도 읽지 못함 | ○ |
| `NOT_ACTIVATED` | 등록된 라이선스 없음 | ○ |
| `NOT_LOADED` | 토큰은 있으나 읽을 수 없음 | ○ |
| `SCHEMA_UNSUPPORTED` | 이 배포가 읽지 않는 스키마 | ○ |
| `REVOKED` | 서버가 폐기함 | ○ |
| `CLOCK_TAMPERED` | 시계가 워터마크보다 뒤로 감 | ○ |
| `INTEGRITY_FAILED` | 바이너리 해시가 기대값과 다름 | ○ |
| `HEARTBEAT_OVERDUE` | 필수 하트비트가 허용 오차 안에 성공하지 못함 | ○ |
| `PRODUCT_MISMATCH` | 다른 제품의 라이선스 | ○ |

`RELEASE_NOT_ENTITLED`가 사용 가능인 것은 의도한 것이다. 상한이 상태 게이트까지 막으면 출입통제가 문 앞에서 멈춘다. 대신 사용 가능한 기능 목록이 비므로 유료 모듈만 닫힌다.

## 머신 바인딩

하드웨어 식별자를 각각 따로 해시해 `sha256:<hex>` 목록으로 만들고, 그 목록이 페이로드에 실린다.

| 플랫폼 | 읽는 값 |
| --- | --- |
| Linux | `/sys/class/dmi/id/product_uuid`, `product_serial`, `/etc/machine-id` |
| macOS | `IOPlatformUUID` |
| Windows | `HKLM\SOFTWARE\Microsoft\Cryptography`의 `MachineGuid` |

대조는 교집합으로 하고, 기준은 **수집 개수**에 둔다.

```
일치 = |수집 ∩ 페이로드|
통과 조건: 일치 ≥ 1  그리고  일치 ≥ ceil(|수집| / 2)
```

| 상황 | 수집 | 일치 | 판정 |
| --- | --- | --- | --- |
| dmi 마운트를 빠뜨린 재배포 | 1 | 1 | 통과 |
| 메인보드 교체 | 3 | 2 | 통과 |
| machine-id만 복사한 다른 머신 | 3 | 1 | 거부 |
| 식별자를 하나도 읽지 못함 | 0 | 0 | `FINGERPRINT_UNAVAILABLE` |

발급 시점 개수를 기준으로 삼으면 식별자를 덜 읽는 환경이 통과할 길이 없다. MAC 주소는 쓰지 않는다 — `--mac-address`로 얼마든지 바꿀 수 있다.

컨테이너에서는 Linux 식별자를 호스트에서 읽기 전용으로 마운트해야 한다.

```
-v /sys/class/dmi/id:/sys/class/dmi/id:ro -v /etc/machine-id:/etc/machine-id:ro
```

## 서명과 키

발급은 Ed25519로 한다. 서명 64바이트, 공개키 32바이트여서 사람이 옮기는 토큰이 짧아지고 검증 공개키를 배포물에 박아도 부담이 없다. 검증기는 RSA-4096 PSS도 함께 읽으므로, 개인키를 하드웨어 모듈에 보관해야 하는 고객이 생겨도 배포된 검증기를 손대지 않는다.

`alg`가 알고리즘을 지정하고 `kid`가 검증 키를 가리킨다. 둘 다 서명이 덮는 영역 안에 있으므로 값을 바꾸면 서명이 깨진다 — 단, 검사 순서를 지킬 때만 그렇다.

```
1. 페이로드에서 alg·kid를 읽는다
2. alg가 이 배포가 허용한 목록에 있는가   없으면 → INVALID_SIGNATURE
3. kid로 공개키를 찾는다                  없으면 → INVALID_SIGNATURE
4. 그 키의 알고리즘이 alg와 같은가          다르면 → INVALID_SIGNATURE
5. 서명을 검증한다
```

2단계와 4단계가 알고리즘 혼동 공격을 막는다.

`kid`는 `<제품군>-<연도>-<일련>` 형태다(`acps-2026-01`). 사람이 읽고 원장의 발급 기록과 맞춰 보는 값이므로 난수가 아니라 순서 있는 이름이다. 배포물은 키를 여럿 담을 수 있고, 그래서 교체가 가능하다 — 교체 기간에는 옛 키와 새 키가 함께 실리고 토큰의 `kid`가 어느 것을 쓸지 정한다.

검증 공개키는 배포물 안에 고정한다. 경로를 바꿀 수 있으면 고객이 자기 키페어로 만든 라이선스를 검증하게 만들 수 있고, 그 순간 서명 검사는 방어가 아니다. 키 교체는 재빌드로 처리한다.

## 게이트

```
gate.state()                     캐시된 판정 결과
gate.require_feature(key)        기능이 없으면 거부
gate.check_quota(code, current)  한도를 넘으면 거부
gate.refresh(evaluation)         코어에 다시 물어 캐시를 갱신
```

판정 결과는 바인딩이 들고 있고, 갱신 시점은 호스트가 정한다 — 기동, 활성화 성공, 하트비트 성공, 주기 재검증이 그 시점이다. 요청마다 도는 게이트는 이 캐시만 읽고 코어를 부르지 않으므로, JSON 경계 비용이 요청 경로에 실리지 않는다.

페이로드에 항목이 없는 한도는 무제한이고, 0은 0이다. 라이선스를 발급한 뒤에 생긴 한도 항목이 그 배포를 갑자기 전부 막아서는 안 된다.

## 활성화

```
호스트                                  코어
제품 키 입력
  ├── fingerprint() ─────────────────▶ 식별자 수집·해시
  ├── activation_request() ──────────▶ 요청 본문 · nonce 생성
  ◀── {body, nonce}
  ├── HTTP POST (호스트가 전송)
  ◀── 서버 응답
  ├── activation_response() ─────────▶ nonce 대조 · 핑거프린트 대조 · 페이로드 해석
  ◀── {licenseToken, activationSecret, ...}
  └── 저장 (호스트)
```

첫 활성화는 제품 키만으로 인증한다. 이후 모든 요청은 활성화 비밀로 서명하며, 전송한 본문 바이트에 대한 base64 HMAC-SHA256을 `X-Activation-Signature` 헤더에 싣는다. 폐쇄망은 같은 함수를 쓰고 전송만 파일이 대신한다.

## SDK가 정하지 않는 것

- **원장·카탈로그·백오피스** — 발급 서버가 소유한다. SDK는 발급 결과의 형식만 안다.
- **제품 어휘** — 기능 키와 한도 코드는 제품의 상수다. SDK는 자유 문자열로 실어 나르기만 한다.
- **번역문** — SDK는 메시지 키와 인자를 돌려주고 번역은 호스트가 한다.
- **바이너리 무결성 계산** — 호스트가 계산하고, SDK는 그 결과를 순서에 놓는다.
